# GET /bookings/mine -- the same query with chaos flag db_drop_index=true
#
# The counterpart to bookings-mine-with-index.txt, captured against the same
# 400,000 seeded bookings as power1@voyager.demo, and the phase 10 exit
# criterion that the plan flips from Index Scan to Seq Scan.
#
# Read the two together. The index turns "find this user's rows" into a seek;
# without it Postgres reads all 400,000 rows, discards 133,359 per worker, and
# sorts what is left -- which is why the row the plan removes by filter is the
# number worth quoting in a demo, not the execution time.
#
# Execution time here (21 ms) is a warm, fully-cached figure on a 6-CPU host:
# the table is 90 MB against 1 GB of shared_buffers, so this is the *cheap*
# version of the pathology. The first, cold run of the same plan measured
# 152 ms. Either way the statement itself goes from 0.05 ms to 14-21 ms --
# between 280x and 400x -- which is the number Database Monitoring shows.
#
# The endpoint does not move nearly that far. GET /bookings/mine goes from
# roughly 8 ms to 21 ms at p95, about 3x, because a JWT check, two HTTP hops
# and JSON serialisation cost several times more than the indexed query does.
# Raising concurrency does not widen the gap: past about four clients the host
# is CPU-bound and the indexed case slows down just as much. See
# scripts/verify-dbm.sh, which asserts both numbers against different
# thresholds for exactly this reason.
